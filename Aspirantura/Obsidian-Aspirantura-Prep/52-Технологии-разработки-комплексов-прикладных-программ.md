# Вопрос 52. Технологии разработки комплексов прикладных программ

← [[00-MOC-Aspirantura-Prep]] · Предыдущий: [[51-Прикладное-программное-обеспечение-математического-моделирования]] · Программа: [[Вопросы#^q52|Вопросы]]

## Краткий ответ (для устного экзамена)

> [!abstract] Простыми словами — вся суть
> **Комплекс прикладных программ (КПП)** — совокупность взаимосвязанных программ, объединённых общей методологией и предназначенных для решения задач определённого класса (например, численного моделирования).
> **Жизненный цикл ПО:** требования → проектирование → реализация → тестирование → внедрение → сопровождение.
> **Технологии разработки:** структурное, модульное, объектно-ориентированное, компонентное программирование.
> **Методологии:** каскадная, итеративная, спиральная, Agile.
> **Архитектура КПП:** модульная структура с чёткими интерфейсами; повторное использование библиотек.
> **Особенности КПП для матмоделирования:** верификация («правильно ли решаем») и валидация («то ли решаем»), тестовые задачи с известными решениями, сгущение сеток.
> **Качество:** надёжность, корректность, эффективность, сопровождаемость; обеспечивается тестированием и документированием.
> Инструменты: системы контроля версий (Git), модульное тестирование, документация.

## Полный ответ

> [!abstract] Связный ответ комиссии
>
> **Определение.**
> КПП — взаимосвязанные **модули** с общей методологией, архитектурой и документацией для класса задач предметной области. Это **система**, не «набор программ».
> Программа — один модуль; библиотека — подпрограммы для встраивания; пакет — готовый инструмент; комплекс — модули + методология + документация.
>
> **Жизненный цикл.**
> От решения о создании до снятия с эксплуатации:
> (1) требования → ТЗ; (2) проектирование → архитектура; (3) реализация → код;
> (4) тестирование; (5) внедрение; (6) **сопровождение** (часто дольше кодирования).
> Цикл не заканчивается написанием кода.
>
> **Методологии.**
> **Каскадная** — этапы строго подряд; для стабильного ТЗ.
> **Итеративная** — циклы с уточнением требований; типична для научных расчётов.
> **Спиральная** — итерации + риски. **Agile** — короткие итерации.
> Каскад не всегда лучше.
>
> **Принципы.**
> Декомпозиция; **модульность**; абстракция; инкапсуляция; повторное использование; минимизация связей.
> **Модуль** — одна подзадача: интерфейс, реализация, документация. Меняем решатель — не трогаем сетку.
>
> **Архитектура.**
> Монолитная, модульная, многоуровневая, компонентная.
> Слои: интерфейс (GUI/CLI) → прикладная логика → численные методы → библиотеки (BLAS, LAPACK, MPI).
> Нужны расширяемость, сопровождаемость, тестируемость.
>
> **Этапы научного КПП.**
> Постановка → матмодель → численный метод → алгоритм → код → **верификация** → **валидация** → документирование.
> Цепочка «физика → математика → метод → код → проверка». Без документации комплекс неполон.
>
> **Качество.**
> Корректность, надёжность, эффективность, сопровождаемость, переносимость, документированность.
> Для науки критичны **корректность** и **воспроизводимость**.
> Тесты: модульные, интеграционные, системные, регрессионные.
>
> **Верификация vs валидация.**
> Верификация — код решает уравнения правильно: аналитика, сгущение сеток ($h\to 0$), балансы, эталоны.
> Валидация — модель адекватна реальности: эксперимент, экспертиза, чувствительность.
> Верификация — про код, валидация — про модель.
>
> **Инструменты.** Git; IDE; Make/CMake; pytest, Google Test; Sphinx, Doxygen; CI.
> Процесс: код → репозиторий → автотесты → сборка → релиз.
>
> **Пример.** КПП «Разностные схемы»: сетка, схема, решатель (прогонка/итерации), визуализация, тесты на эталонах.
>
> **Комиссии.** Определение КПП; жизненный цикл и модели процесса; модульность и слои; верификация/валидация; пример модулей численного комплекса.

## 1. Понятие комплекса прикладных программ

### Определение

**Формулировка (учебник):** комплекс прикладных программ (КПП) — совокупность взаимосвязанных программных модулей, объединённых общей методологией, единой архитектурой и предназначенных для решения широкого класса задач определённой предметной области.

### Отличие от смежных понятий

| Понятие                       | Характеристика                                      |
| ----------------------------- | --------------------------------------------------- |
| **Программа**                 | отдельный исполняемый модуль                        |
| **Библиотека**                | набор подпрограмм для встраивания                   |
| **Пакет прикладных программ** | готовый инструмент с интерфейсом                    |
| **Комплекс программ**         | архитектура из модулей + методология + документация |

> [!tip] Простыми словами
> КПП — это не просто «набор программ», а **система**: модули, интерфейсы, документация, методология использования. Как конструктор с инструкцией.

### Примеры КПП в матмоделировании

| КПП                         | Назначение                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------- | ------------ |
| Комплексы разностных схем   | решение УрЧП ([[46-Разностные-методы-решения-нестационарных-задач-математической-физики | Вопрос 46]]) |
| Пакеты линейной алгебры     | решение СЛАУ ([[38-СЛАУ-численные-методы                                                | Вопрос 38]]) |
| Комплексы CFD-моделирования | гидродинамика, теплообмен                                                               |
| Библиотеки ОДУ              | решение задачи Коши ([[40-Численные-методы-решения-задачи-Коши-для-систем-ОДУ           | Вопрос 40]]) |

## 2. Жизненный цикл программного обеспечения

### Определение

**Формулировка (учебник):** жизненный цикл ПО — последовательность этапов разработки, эксплуатации и сопровождения программы от момента принятия решения о её создании до прекращения использования.

### Основные этапы

| Этап                     | Содержание                      | Результат           |
| ------------------------ | ------------------------------- | ------------------- |
| **1. Анализ требований** | что должна делать программа     | техническое задание |
| **2. Проектирование**    | архитектура, модули, интерфейсы | проект архитектуры  |
| **3. Реализация**        | написание кода                  | исходный код        |
| **4. Тестирование**      | проверка корректности           | отчёты, исправления |
| **5. Внедрение**         | установка, обучение             | рабочий продукт     |
| **6. Сопровождение**     | обновления, исправления         | новые версии        |

> [!tip] Простыми словами
> Жизненный цикл — «путь программы от идеи до архива»: сначала понимаем, что нужно, потом проектируем, пишем, проверяем, внедряем и поддерживаем.

## 3. Методологии разработки

### Основные модели

| Модель          | Суть                         | Когда применять                     |
| --------------- | ---------------------------- | ----------------------------------- |
| **Каскадная**   | этапы строго последовательны | стабильные требования, гос. проекты |
| **Итеративная** | повторение циклов разработки | уточняющиеся требования             |
| **Спиральная**  | итерации + анализ рисков     | сложные проекты с рисками           |
| **Agile**       | короткие итерации, гибкость  | быстро меняющиеся требования        |

### Каскадная модель

$$
\text{Требования} \to \text{Проект} \to \text{Код} \to \text{Тесты} \to \text{Внедрение}
$$

### Итеративная модель

$$
\text{Итерация 1} \to \text{Итерация 2} \to \cdots \to \text{Финальный продукт}
$$

Каждая итерация: мини-цикл (анализ → код → тесты → обратная связь).

> [!important] На экзамене
> В научных расчётах часто используется **итеративная** модель: требования уточняются по мере получения первых результатов. Каскадная модель подходит для задач с чётко определённым ТЗ.

## 4. Принципы проектирования КПП

### Основные принципы

| Принцип                     | Суть                                                                           |
| --------------------------- | ------------------------------------------------------------------------------ | ------------ |
| **Декомпозиция**            | разделение задачи на подзадачи                                                 |
| **Модульность**             | независимые модули с чёткими интерфейсами                                      |
| **Абстракция**              | выделение существенного, сокрытие деталей                                      |
| **Инкапсуляция**            | данные и методы вместе ([[50-Основы-объектно-ориентированного-программирования | Вопрос 50]]) |
| **Повторное использование** | библиотеки, компоненты                                                         |
| **Минимизация связей**      | модули общаются через интерфейсы                                               |

### Модульная структура

**Формулировка (учебник):** модуль — функционально законченный фрагмент программы, имеющий чётко определённый интерфейс и реализующий одну подзадачу.

| Компонент модуля | Назначение                     |
| ---------------- | ------------------------------ |
| Интерфейс        | что модуль делает (вход/выход) |
| Реализация       | как модуль это делает          |
| Документация     | описание использования         |

### Пример декомпозиции для разностной схемы

```
КПП «Разностные схемы»
├── Модуль сетки       — построение сетки, граничные условия
├── Модуль схемы       — реализация разностного оператора
├── Модуль решателя    — решение СЛАУ (прогонка, итерации)
├── Модуль визуализации — вывод результатов
└── Модуль тестов      — проверка на эталонных задачах
```

> [!tip] Простыми словами
> Каждый модуль делает одну вещь хорошо. Меняем решатель — не трогаем сетку. Это и есть модульность.

## 5. Архитектура КПП

### Основные виды архитектуры

| Архитектура        | Характеристика                    | Пример                        |
| ------------------ | --------------------------------- | ----------------------------- |
| **Монолитная**     | всё в одной программе             | простые расчётные скрипты     |
| **Модульная**      | набор независимых модулей         | научные библиотеки            |
| **Многоуровневая** | слои: данные → логика → интерфейс | крупные системы моделирования |
| **Компонентная**   | переиспользуемые компоненты       | плагины, библиотеки           |

### Слои типичного КПП матмоделирования

$$
\text{Интерфейс пользователя} \;\to\; \text{Прикладная логика} \;\to\; \text{Численные методы} \;\to\; \text{Библиотеки низкого уровня}
$$

| Слой               | Примеры                               |
| ------------------ | ------------------------------------- |
| Интерфейс          | GUI, CLI, скрипты                     |
| Прикладная логика  | постановка задачи, параметры модели   |
| Численные методы   | разностные схемы, итерационные методы |
| Базовые библиотеки | BLAS, LAPACK, MPI                     |

> [!important] На экзамене
> Архитектура КПП должна обеспечивать: расширяемость (новые методы), сопровождаемость (понятность кода), тестируемость (проверка модулей).

## 6. Этапы разработки КПП для математического моделирования

### Специфика научного ПО

**Формулировка (учебник):** разработка КПП для матмоделирования включает этапы, отражающие связь с математической моделью и численным методом:

| 7. Валидация             | проверка адекватности модели     |

## 7. Тестирование и качество ПО

### Уровни тестирования

| Уровень              | Что проверяется                       |
| -------------------- | ------------------------------------- |
| **Модульное** (unit) | отдельный модуль/функция              |
| **Интеграционное**   | взаимодействие модулей                |
| **Системное**        | весь комплекс в целом                 |
| **Регрессионное**    | что новые изменения не сломали старое |

### Критерии качества ПО

| Критерий                | Суть                                  |
| ----------------------- | ------------------------------------- |
| **Корректность**        | программа делает то, что задумано     |
| **Надёжность**          | устойчивость к ошибкам входных данных |
| **Эффективность**       | разумные время и память               |
| **Сопровождаемость**    | лёгкость внесения изменений           |
| **Переносимость**       | работа на разных платформах           |
| **Документированность** | понятность для пользователя           |

> [!important] На экзамене
> Для научных расчётов критична **корректность** и **воспроизводимость** результатов: одинаковые входные данные должны давать одинаковый результат.

## 8. Верификация и валидация в матмоделировании

### Определения

**Формулировка (учебник):**

- **верификация** — проверка корректности численной реализации модели: «правильно ли мы решили уравнения?»;
- **валидация** — проверка адекватности модели реальности: «те ли уравнения мы решили?».

### Методы верификации

| Метод                 | Суть                                      |
| --------------------- | ----------------------------------------- |
| Тестовые задачи       | задачи с известным аналитическим решением |
| Сгущение сеток        | проверка сходимости при $h \to 0$         |
| Балансные соотношения | проверка законов сохранения               |
| Сравнение с эталонами | результаты из литературы                  |

### Методы валидации

| Метод                     | Суть                              |
| ------------------------- | --------------------------------- |
| Сравнение с экспериментом | данные измерений                  |
| Экспертная оценка         | соответствие физическим ожиданиям |
| Анализ чувствительности   | реакция на параметры модели       |

> [!tip] Простыми словами
> Верификация: «код не врёт» — проверяем на задачах, где знаем ответ. Валидация: «модель не врёт» — сверяем с реальностью.

## 9. Инструменты разработки

### Основные инструменты

| Инструмент                      | Назначение                     | Примеры                   |
| ------------------------------- | ------------------------------ | ------------------------- |
| **Системы контроля версий**     | отслеживание изменений         | Git, Mercurial            |
| **Среды разработки (IDE)**      | редактор + отладчик            | VS Code, PyCharm          |
| **Сборщики**                    | автоматизация сборки           | Make, CMake               |
| **Тестовые фреймворки**         | автоматические тесты           | pytest, Google Test       |
| **Документация**                | описание использования         | Sphinx, Doxygen           |
| **Непрерывная интеграция (CI)** | автотесты при каждом изменении | GitHub Actions, GitLab CI |

### Типовой рабочий процесс

$$
\text{Код} \;\xrightarrow{\text{Git}}\; \text{Репозиторий} \;\xrightarrow{\text{CI}}\; \text{Автотесты} \;\xrightarrow{\text{Сборка}}\; \text{Релиз}
$$

> [!tip] Простыми словами
> Git хранит историю изменений; автотесты проверяют, что ничего не сломалось; документация помогает пользователю. Это «гигиена разработки».

## 10. Типичные ошибки на экзамене

> [!failure] Частые ошибки
> Путать **программу** (один модуль) и **комплекс программ** (система модулей с методологией).
> Считать, что жизненный цикл заканчивается на этапе написания кода — сопровождение часто занимает больше времени.
> Не различать верификацию и валидацию: верификация — про код, валидация — про модель.
> Забывать про документирование — без него КПП не является полноценным комплексом.
> Утверждать, что каскадная модель всегда лучше — выбор методологии зависит от задачи.
> Не упоминать тестирование — корректность научных расчётов критична.
> Не приводить примеры архитектуры и модулей.

## 12. Контрольные вопросы

### 1. Комплекс прикладных программ

- [x] Что такое комплекс прикладных программ? Чем он отличается от отдельной программы?

**Ответ.** КПП — совокупность взаимосвязанных модулей с общей методологией, архитектурой и документацией для класса задач предметной области. **Программа** — один исполняемый модуль; **библиотека** — подпрограммы для встраивания; **пакет** — готовый инструмент с интерфейсом; **комплекс** — система модулей + методология + документация.

---

### 2. Жизненный цикл ПО

- [x] Перечислите этапы жизненного цикла ПО.

**Ответ.** От решения о создании до снятия с эксплуатации:
1. анализ требований (ТЗ);
2. проектирование (архитектура);
3. реализация (код);
4. тестирование;
5. внедрение;
6. сопровождение (часто дольше кодирования).

---

### 3. Каскадная и итеративная модели

- [x] Чем каскадная модель отличается от итеративной?

**Ответ.** **Каскад:** этапы строго подряд (требования $\to$ проект $\to$ код $\to$ тесты $\to$ внедрение); для стабильного ТЗ. **Итеративная:** циклы мини-разработки с уточнением требований; типична для научных расчётов. Также спиральная (риски) и Agile (короткие спринты). Каскад не всегда лучше.

---

### 4. Принципы проектирования

- [x] Назовите основные принципы проектирования КПП.

**Ответ.** Декомпозиция; **модульность** (интерфейсы); абстракция; инкапсуляция; повторное использование библиотек; минимизация связей (общение только через интерфейсы).

---

### 5. Модуль

- [x] Что такое модуль? Какие у него компоненты?

**Ответ.** Функционально законченный фрагмент с чётким интерфейсом, одна подзадача. Компоненты: **интерфейс** (вход/выход), **реализация** (как), **документация**. Пример КПП схем: сетка, схема, решатель, визуализация, тесты — меняем решатель, не трогая сетку.

---

### 6. Архитектура КПП моделирования

- [x] Какова архитектура типичного КПП матмоделирования?

**Ответ.** Слои:
$$
\text{интерфейс (GUI/CLI)}\to\text{прикладная логика}\to\text{численные методы}\to\text{библиотеки (BLAS, LAPACK, MPI)}.
$$
Виды: монолит, модульная, многоуровневая, компонентная. Требования: расширяемость, сопровождаемость, тестируемость.

---

### 7. Этапы разработки КПП моделирования

- [x] Перечислите этапы разработки КПП для матмоделирования.

**Ответ.** Специфика научного ПО: постановка $\to$ матмодель $\to$ численный метод $\to$ алгоритм $\to$ код $\to$ **верификация** $\to$ **валидация** $\to$ документирование. Цепочка «физика $\to$ математика $\to$ метод $\to$ код $\to$ проверка»; пропуск звена делает результат ненадёжным.

---

### 8. Верификация и валидация

- [x] Чем верификация отличается от валидации?

**Ответ.** **Верификация** — код решает уравнения правильно (тестовые задачи, сгущение сеток $h\to 0$, балансы, эталоны). **Валидация** — модель адекватна реальности (эксперимент, экспертиза, чувствительность). Верификация — про код, валидация — про модель.

---

### 9. Критерии качества ПО

- [x] Каковы критерии качества ПО?

**Ответ.** Корректность, надёжность, эффективность, сопровождаемость, переносимость, документированность. Для науки критичны **корректность** и **воспроизводимость**. Уровни тестов: модульные, интеграционные, системные, регрессионные.

---

### 10. Инструменты разработки

- [x] Какие инструменты разработки вы знаете?

**Ответ.** VCS (**Git**); IDE; сборщики (Make, CMake); тесты (pytest, Google Test); документация (Sphinx, Doxygen); CI (GitHub Actions, GitLab CI). Процесс: код $\xrightarrow{\mathrm{Git}}$ репозиторий $\xrightarrow{\mathrm{CI}}$ автотесты $\to$ релиз.

### Образец устного ответа

> [!example] Устно (3–5 минут)
>
