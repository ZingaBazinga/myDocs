# Архитектура, DevOps, Soft skills — Middle

---

## Архитектура

### Feature-Sliced Design (FSD)

Слои сверху вниз: **app → pages → widgets → features → entities → shared**. Изоляция — импорт только «вниз», не между фичами напрямую. Слайсы внутри слоя — по бизнес-смыслу; сегменты `ui`, `model`, `api`, `lib`.

### Clean Architecture (на фронте)

**Entities** — доменные типы; **use cases** — сценарии; **adapters** — API/UI; **infrastructure** — HTTP-клиент. Зависимости направлены внутрь к политике.

### Atomic Design

**Atoms → molecules → organisms → templates → pages** — масштабирование UI-кита; не смешивай бизнес-логику глубоко в atoms без необходимости.

### Компонентная архитектура

Декомпозиция по ответственности; **smart vs dumb** (контейнер/презентация); **compound components** для связанных частей (Tabs, Select).

### Render props, HOC, custom hooks

Все способы шаринга логики; в React 2020+ чаще **hooks**; HOC усложняют типизацию и дерево; render props вербы но явны.

### Инверсия зависимостей

Зависеть от интерфейсов сервисов; подмена в тестах и смена реализации без правки UI.

### Монорепо vs полирепо

Монорепо — атомарные изменения, общие инструменты; полирепо — изоляция релизов. Trade-offs по размеру оргструктуры и CI.

### API Layer

Единая обёртка над fetch/axios: базовый URL, **interceptors** (токены), маппинг DTO→domain, единая обработка ошибок.

### Error boundaries и глобальные ошибки

Границы на уровне маршрутов/виджетов + глобальный логгер (Sentry); для асинхронных ошибок — отдельная подписка.

### Feature flags

Тумблеры фич для постепенного rollout и A/B; хранение состояния флага, синхронизация с аналитикой.

### Маршрутизация

**Nested routes**, **layouts**, **guards** (auth), **code splitting** по маршрутам.

## DevOps и инфраструктура

### Git продвинутый

**Interactive rebase** — чистая история; **cherry-pick** — перенос коммитов; **bisect** — поиск ломающего коммита; **reflog** — спасение после «ошибся веткой»; **worktrees** — несколько рабочих копий; **submodules** — осторожно, сложны в саппорте.

### Git Flow

Ветки `main/develop`, `feature/*`, `release/*`, `hotfix/*` — формализм для релизов; многие команды упрощают до trunk-based + короткоживущие ветки.

### CI/CD GitLab

**`.gitlab-ci.yml`**: **stages** (build, test, deploy), **jobs**, **artifacts** между стадиями, **cache** для `node_modules`, правила `rules`/`only`.

### Docker для фронта

**Multi-stage build**: builder со всеми devDeps → nginx/serve со статикой. **`.dockerignore`** — не копировать `node_modules` с хоста. Минимум слоёв, порядок COPY для кэша.

### Nginx для SPA

**`try_files $uri /index.html`** — fallback для client-side routing; **gzip/brotli**, **proxy_pass** к API, заголовки безопасности.

### CDN

Кэш на edge ближе к пользователю; **инвалидация** по версии файла или purge API.

### Sentry

Интеграция SDK, **source maps** для стектрейсов, контекст релиза, breadcrumbs.

### Semantic versioning и conventional commits

**major.minor.patch**; **Conventional Commits** (`feat:`, `fix:`) → автогенерация changelog.

*(AppsFlyer из матрицы — уточни в компании, как именно встроена аналитика.)*

## Soft skills Middle {#Soft skills Middle}

Как говорить на ревью: краткая формула **ситуация → действие → результат**.

- **Самостоятельная декомпозиция** — разбиваешь эпик на задачи, выделяешь зависимости и риски.
- **Код-ревью** — конструктив: что хорошо, что изменить, почему; приоритет по критичности.
- **Менторство** — объясняешь «почему», pair programming, даёшь читаемые примеры.
- **Приоритеты** — при перегрузе предлагаешь урезать скоуп или сдвиг с обоснованием.
- **Оценки ±20%** — учитываешь неопределённость, буфер на интеграции и ревью.
- **Аргументация** — связываешь техническое решение с метриками/риском/сроком.
- **Найм** — секции собеседований по чек-листу, без «ловушек ради ловушек».
- **Статус** — прозрачно: что сделано, что в работе, блокеры **до** дедлайна.
- **Документация** — README, **ADR** для решений, описание API для фронта.
- **Продуктовый контекст** — кто пользователь, зачем фича; предлагаешь улучшения процесса.

**Владение фичей end-to-end** — от уточнения требований до мониторинга после релиза.
